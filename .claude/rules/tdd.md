# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다. 예외는 아래 "적용 기준"에 명시된 것뿐이다.

## 1. 적용 기준

### 반드시 TDD를 적용하는 대상

- **비즈니스 로직**: 조건 분기, 계산, 상태 전이, 데이터 변환
- **API**: 요청 검증, 응답 형태, 에러 처리, 외부 서비스 호출 결과 처리
- **유틸 함수**: 순수 함수, 파서, 포매터, 정규화 로직
- **버그 수정**: 버그를 재현하는 실패 테스트를 먼저 작성하고, 그 테스트를 통과시켜 수정한다

### TDD가 불필요한 대상

- **타입 정의**: `type`, `interface`, 선언 파일
- **설정 파일**: `package.json`, `tsconfig`, `vite.config`, ESLint 설정 등
- **순수 UI**: 로직 없는 마크업, 스타일(CSS), 레이아웃, 문구 변경
- **SQL**: 스키마·마이그레이션·단순 쿼리 정의

불필요 대상이라도 그 안에 **분기나 계산이 들어가면 해당 로직은 TDD 대상**이다. 판단이 애매하면 적용한다.

## 2. RED - GREEN - REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 검증하지 않는다. 테스트 이름에 "그리고"가 들어가면 쪼갠다.
- 테스트는 구현이 아니라 **외부에서 관찰되는 동작**을 검증한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 설정 문제로 실패한 것은 RED가 아니다. 그 오류를 고친 뒤 다시 실행해서 올바른 이유로 실패하는지 확인한다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트나 동작 정의를 고친다.

### GREEN: 최소한의 코드로 통과

- **테스트를 통과시키는 최소한의 코드만 작성한다.** **YAGNI**: 지금 테스트가 요구하지 않는 기능, 옵션, 확장 포인트를 넣지 않는다.
- 하드코딩으로 먼저 통과시켜도 된다. 다음 RED가 일반화를 강제한다.
- **신규 테스트와 기존 테스트를 모두 실행해서 전부 통과하는지 확인한다.** 하나라도 실패하면 GREEN이 아니다.
- 테스트를 수정해서 통과시키지 않는다. 테스트가 틀렸다면 RED로 돌아가 테스트부터 고친다.

### REFACTOR: 구조 개선

- **중복 제거, 이름 개선, 헬퍼 추출**만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 변경 단위마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.
- 리팩터링할 것이 없으면 건너뛰어도 된다. 이 단계에서만 허용되는 생략이다.

### 반복

다음 동작에 대해 **RED로 돌아간다.** 요구된 동작을 모두 구현할 때까지 사이클을 반복한다.

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 임시 파일, 다른 브랜치·stash 보관, 복사해 두고 보면서 다시 쓰기 모두 포함한다.
- 삭제한 코드를 보고 테스트를 작성하지 않는다. 요구사항에서 테스트를 도출한다.

## 4. 변명 차단표

| 변명 | 반론 |
| --- | --- |
| 너무 단순해서 테스트가 필요 없다 | 단순한 코드는 테스트도 30초면 쓴다. 단순하다고 믿은 코드에서 가장 많이 틀린다. 지금 단순해도 나중에 바뀌고, 그때 테스트가 회귀를 막는다. |
| 나중에 테스트를 추가하겠다 | 나중에 쓴 테스트는 구현에 맞춰 쓰게 되어 버그를 못 잡는다. 처음부터 통과하므로 실패를 본 적도 없다. 그리고 그 "나중"은 오지 않는다. |
| 시간이 없다 | 테스트 없이 낸 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. 급할수록 회귀 위험이 커지므로 테스트가 더 필요하다. |
| 이미 짠 코드를 삭제하면 낭비다 | 매몰 비용이다. 검증 안 된 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 이미 아는 문제를 다시 푸는 건 빠르다. |
| 프로토타입이라 괜찮다 | 프로토타입은 버려지지 않고 제품이 된다. 버릴 코드라면 어차피 아까울 것이 없으니 삭제 규칙을 따르는 데 비용이 들지 않는다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙(테스트 명령어, 위치, 네이밍, 적용 범위 등)이 있으면 **그 규칙이 이 파일보다 우선한다.**
- **이 파일은 기본값(fallback)이다.** 프로젝트 규칙이 다루지 않는 부분만 이 파일을 따른다.
- 우선되는 것은 프로젝트의 구체적 설정(명령어, 경로, 도구)이다. 프로젝트 규칙이 침묵하는 한, RED-GREEN-REFACTOR의 순서와 삭제 강제 규칙은 그대로 적용된다.
