# Commit

변경사항을 분석해 컨벤션에 맞는 한국어 커밋 메시지로 커밋한다.

## 모드

- **기본(자동)**: 커밋 요청 자체를 승인으로 본다. 분석 → 분류 → 메시지 작성 후 바로 커밋하고 결과를 보고한다.
- **확인(`--confirm`)**: 커밋 전에 메시지와 파일 목록을 보여주고 승인을 받는다.

자동 모드라도 아래 경우에는 커밋하지 않고 사용자에게 먼저 묻는다.

- 한 파일 안에 서로 다른 목적의 변경이 섞여 있어 나누는 기준이 모호할 때
- 제외 대상 파일(`.env`, 키·토큰 등)이 stage되어 있어 어떻게 할지 정해야 할 때
- 변경 규모가 비정상적으로 클 때 (예: 수십 개 파일 삭제, 대용량 바이너리 추가)

## 절차

### 1. 변경사항 분석

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 확인
```

- 새 파일(untracked)은 내용을 직접 읽어 확인한다.
- git 저장소가 아니면(`fatal: not a git repository`) 커밋하지 않고 사용자에게 알린다. `git init`은 사용자가 요청할 때만 한다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 가진다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 같은 목적의 코드, 테스트, 스타일은 한 커밋에 묶는다.
- 단위마다 포함할 파일 목록을 정한다. 파일 하나 안에 서로 다른 목적의 변경이 섞여 있으면 사용자에게 알린다.
- 커밋하면 안 되는 파일(`.env`, 키·토큰, `node_modules`, 빌드 산출물, 대용량 바이너리)이 있으면 제외하고 알린다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 용도 |
| --- | --- |
| feat | 새 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 잡무 |

- 요약은 한국어로 50자 안팎, 마침표 없이 쓴다. 무엇을 했는지 현재형 또는 명사형으로 쓴다. 예: `feat: 프롬프트 예시 칩 추가`
- 본문은 "왜" 바꿨는지가 diff만으로 드러나지 않을 때만 쓴다.
- 기존 로그에 이미 다른 규칙이 뚜렷하면 type 체계는 유지하되 그 스타일에 맞춘다.

### 4. 커밋

아래 형식으로 계획을 정리한다.

```
커밋 1/2
  메시지: feat: ...
  파일: src/a.ts, src/b.ts
커밋 2/2
  메시지: chore: ...
  파일: package.json
```

- **자동 모드**: 계획을 출력하고 바로 단위별로 `git add <파일들>` → `git commit`을 실행한다.
- **확인 모드**: 계획을 보여주고 승인을 받은 뒤에만 실행한다. 메시지나 분류를 고치라고 하면 반영해서 다시 확인받는다.
- 어느 모드든 `git add -A`나 `git add .`는 쓰지 않는다.
- 커밋 메시지 끝에는 세션이 안내하는 attribution 줄(Co-Authored-By)이 있으면 붙인다. HEREDOC로 여러 줄 메시지를 넘긴다.
- hook이 실패하면 `--no-verify`로 우회하지 않는다. 원인을 고치고 새 커밋으로 만든다.
- 기존 커밋 amend, push, force 옵션은 사용자가 요청하지 않으면 하지 않는다.
- 끝나면 `git log --oneline -n <커밋 수>`로 결과를 보여준다. 자동 모드에서는 되돌리는 방법(`git reset --soft HEAD~<커밋 수>`)도 한 줄로 알려준다.
